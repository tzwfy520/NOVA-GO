# 项目后端开发规范

## 1. 日志开发规范

### 1.1 目标与原则

- 日志必须可检索、可聚合、可关联：同一链路应可通过 `request_id`、`task_id` 等字段串起来
- 默认输出结构化日志（JSON 模式下字段为独立 key），避免把关键字段拼进 `msg`
- `msg` 只放人类可读摘要；字段放在 key-value 中
- 生产环境默认避免输出大段回显与敏感内容

### 1.2 结构化日志写法

- 推荐写法：`logger.Info("事件名", "k1", v1, "k2", v2, ...)`
  - 第 1 个参数为 `msg`（字符串）
  - 后续按 `key, value` 成对传入
  - `key` 必须为非空字符串
- 禁止写法：把关键字段拼接成一个长字符串（例如 `fmt.Sprintf("...%v...", x)`），导致字段不可聚合

### 1.3 字段规范（Schema）

**必须字段（按场景）**

- HTTP 请求：`request_id`、`method`、`path`、`status`、`duration`、`client_ip`、`user_agent`
- 任务执行：`task_id`、`log_type`（collector/backup/format/deploy）、必要时加 `device_ip`、`device_name`、`device_platform`
- 命令执行：`command`、`exit_code`、`duration_ms`、成功/失败时附 `error`

**建议字段**

- `module`：模块名（例如 server/http/collector/backup/deploy/format/simulate）
- `trace`：一次性排障需要的补充字段（仅在 debug 或必要错误场景）

### 1.4 日志等级

- `debug`：开发/联调细节；默认不在生产开启；不得包含密钥/密码
- `info`：关键业务事件与状态变化（启动、配置加载、任务开始/结束、统计摘要）
- `warn`：可恢复或需要关注的异常（重试、降级、外部依赖短暂失败）
- `error`：请求失败、任务失败、不可忽略的错误；必须带 `error` 字段
- `fatal`：不可恢复错误导致进程退出（初始化失败等），使用时必须谨慎

### 1.5 敏感信息与大字段控制

- 禁止在日志中输出：密码、口令、AccessKey/SecretKey、Token、私钥等
- 命令回显/配置内容属于高风险大字段：
  - 默认只记录摘要（行数、前后 N 行、hash、耗时）
  - 需要完整内容时写入任务日志文件或对象存储，并在应用日志中记录引用（路径/URI）

### 1.6 任务日志文件

- 任务日志文件用于承载“逐命令追踪/大字段输出”，与全局应用日志分离
- 任务日志必须包含 `task_id` 与 `log_type`，建议使用 JSON Lines（每行一个 JSON）
- 任务日志文件必须受清理策略治理（按天/按文件数/按总大小），避免磁盘无限增长

### 1.7 配置与热更新

- 日志配置以 `configs/config.yaml` 的 `log.*` 为准
- 修改日志配置后应可热更新生效，且不应导致并发写日志异常
