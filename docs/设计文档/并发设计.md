# nova-go 并发与高可用设计方案

## 1. 概述

本文档旨在梳理 nova-go 项目当前的并发模型，识别存在的安全隐患与性能瓶颈，并提出高效、安全的并发设计方案。主要聚焦于 SSH 客户端连接管理、连接池并发控制以及服务层的并发调度。

## 2. 现状分析与问题诊断

### 2.1 SSH 客户端 (pkg/ssh/client.go)

**并发模型**：
- `Client` 结构体包含共享的 `*ssh.Client` 连接实例。
- 理论上支持多协程共享同一个 `Client` 实例，但实现上存在缺陷。

**存在的问题**：
1.  **Panic 隐患 (空指针解引用)**：
    -   在 `newSessionWithRetry` 中，重连逻辑 (`Close` + `Connect`) 忽略了 `Connect` 的返回值。若重连失败，`c.connection` 保持为 `nil`，随后的 `c.connection.NewSession()` 调用直接导致 Panic。
2.  **数据竞争 (Data Race)**：
    -   `newSessionWithRetry` 读取 `c.connection` 时未加读锁 (`RLock`)。
    -   `keepAlive` 协程与主执行协程并发运行，`keepAlive` 可能在检测到故障时调用 `Close` 将 `c.connection` 置空，而主协程正试图使用它，导致竞态条件。
3.  **KeepAlive 上下文生命周期问题**：
    -   在 `newSessionWithRetry` 中建立连接时使用了临时的 `ConnectTimeout` 上下文。一旦连接建立完成，该上下文即被取消，导致依赖该上下文的 `keepAlive` 协程立即退出。这意味着重连后的连接实际上失去了保活机制。

### 2.2 SSH 连接池 (pkg/ssh/pool.go)

**并发模型**：
- 维护 `map[string]*pooledConnection`，以 `host:port@user` 为键。
- 旨在复用连接，减少握手开销。

**存在的问题**：
1.  **严重的连接泄漏 (Connection Leak)**：
    -   **场景**：当多个任务并发采集同一台设备时。
    -   **过程**：
        1.  任务 A 获取连接 `Conn A` (key="device1")，标记 `inUse=true`。
        2.  任务 B 请求同一设备的连接。Pool 发现 `Conn A` 正在使用 (`inUse=true`)，目前的逻辑是**从 map 中删除 Conn A**，并创建新连接 `Conn B` 放入 map (覆盖 key)。
        3.  任务 A 完成，调用 `ReleaseConnection`。Pool 根据 key 查找，找到的是 `Conn B`。
        4.  Pool 将 `Conn B` 标记为 `inUse=false`（错误地释放了 B 的锁状态）。
        5.  **后果**：`Conn A` 被从 map 中移除且从未被显式关闭（也就无法归还），成为“孤儿连接”，导致 TCP 连接泄漏。同时，`Conn B` 的状态被错误修改，可能导致后续任务拿到一个实际上正在被使用的连接，引发更严重的并发冲突。
2.  **并发策略低效**：
    -   当前的“遇忙即弃”策略（Drop-if-busy）导致高并发下连接复用率极低，且频繁创建/销毁连接（甚至泄漏），违背了连接池的设计初衷。

### 2.3 服务层 (internal/service)

**并发模型**：
- `CollectorService` 使用 worker channel 控制并发度。
- 每个任务独立获取/释放连接。

**问题**：
- 依赖于底层的 Pool 和 Client，受到底层缺陷的直接影响。

## 3. 高可用并发设计

### 3.1 SSH 客户端重构设计

**目标**：保证 `Client` 内部状态的原子性与线程安全，杜绝 Panic。

**方案**：
1.  **严格的读写锁保护**：
    -   所有对 `c.connection` 的访问必须加锁。
    -   读操作（`IsConnected`, `NewSession` 前的检查）使用 `RLock`。
    -   写操作（`Connect`, `Close`）使用 `Lock`。
    -   在 `newSessionWithRetry` 中，使用局部变量持有 `ssh.Client` 指针，或者在持有读锁期间创建 Session，防止中途变为 nil。
2.  **健壮的重连逻辑**：
    -   `newSessionWithRetry` 必须检查 `Connect` 的错误。
    -   如果重连失败，应根据策略决定是继续退避还是返回错误，绝不能在连接未就绪时继续执行。
3.  **独立的 KeepAlive 上下文**：
    -   `Client` 应维护一个独立的 `context.Context` 用于管理后台协程（如 `keepAlive`）的生命周期，该上下文仅在 `Close` 时取消，而不受 `Connect` 传入的临时上下文影响。

### 3.2 SSH 连接池重构设计

**目标**：解决连接泄漏，实现真正的连接复用与排队机制。

**方案**：
1.  **修正释放逻辑**：
    -   `ReleaseConnection` 必须验证待释放的连接是否就是当前 map 中存储的连接。
    -   或者，`ReleaseConnection` 应该接收具体的 `*Client` 实例作为参数，而不仅仅是 `ConnectionInfo`。
2.  **优化并发获取策略**：
    -   **策略 A（排队复用 - 推荐）**：如果连接繁忙 (`inUse=true`)，调用者进入等待队列（使用 `Cond` 或 `Channel`），直到连接可用或超时。这能最大化复用，降低设备压力。
    -   **策略 B（临时连接）**：如果连接繁忙，不修改 map 中的现有连接，而是直接返回一个**不入池**的临时连接（Transient Connection）。该连接在使用完毕后直接关闭，不归还给池。
    -   **选型**：考虑到网络设备通常限制 SSH 连接数，**策略 A** 更优，但实现复杂度较高。为了快速修复且保证高可用，可以采用 **策略 B + 泄漏修复** 的组合：
        -   池中只维护一个“主连接”。
        -   如果主连接空闲，复用之。
        -   如果主连接繁忙，创建临时连接执行任务，任务结束后立即关闭临时连接（不影响池中主连接）。
        -   **关键点**：临时连接绝不能覆盖池中的主连接记录。

### 3.3 详细设计规范

#### 3.3.1 Client 锁机制
```go
func (c *Client) getClient() (*ssh.Client, error) {
    c.mutex.RLock()
    defer c.mutex.RUnlock()
    if c.connection == nil {
        return nil, fmt.Errorf("not connected")
    }
    return c.connection, nil
}
```

#### 3.3.2 Pool 获取逻辑 (修正版)
```go
func (p *Pool) GetConnection(ctx context.Context, info *ConnectionInfo) (*Client, bool, error) {
    key := p.getConnectionKey(info)
    p.mutex.Lock()
    
    // 1. 尝试复用
    if conn, exists := p.connections[key]; exists {
        if !conn.inUse && conn.client.IsConnected() {
            conn.inUse = true
            p.mutex.Unlock()
            return conn.client, false, nil // false 表示不是临时连接
        }
        // 如果连接已死，清理之
        if !conn.client.IsConnected() {
            delete(p.connections, key)
        }
    }
    
    // 2. 无法复用（不存在或繁忙），决策：
    // 这里采用策略：若繁忙则创建临时连接，不入池
    if _, exists := p.connections[key]; exists {
        p.mutex.Unlock()
        // 创建临时连接
        client := NewClient(p.config)
        if err := client.Connect(ctx, info); err != nil {
            return nil, false, err
        }
        return client, true, nil // true 表示是临时连接，需由调用方负责关闭
    }

    // 3. 不存在，创建新连接入池
    client := NewClient(p.config)
    // 注意：Connect 耗时较长，持有锁进行 Connect 会阻塞整个池。
    // 优化：先占位，解锁 Connect，再加锁更新（需处理并发竞争）
    // 简化版：暂且持有锁（简单安全，但在高并发新建连接时有瓶颈）
    if err := client.Connect(ctx, info); err != nil {
        p.mutex.Unlock()
        return nil, false, err
    }
    
    p.connections[key] = &pooledConnection{
        client: client,
        inUse:  true,
        // ...
    }
    p.mutex.Unlock()
    return client, false, nil
}
```

#### 3.3.3 Pool 释放逻辑 (修正版)
```go
// ReleaseConnection 仅处理池化连接的归还
func (p *Pool) ReleaseConnection(client *Client) {
    // 需反向查找 key 或在 Client 中存储 key
    // ...
}
```
*更优方案*：`Pool` 返回一个包装器 `PooledClient`，包含 `Release()` 方法。
对于现有代码改动最小的方案：`InteractBasic` 知道它拿到的是否是临时连接。

## 4. 实施计划

1.  **阶段一：修复 SSH Client (高优先级)**
    -   修复 `newSessionWithRetry` 的 Panic 问题。
    -   引入 `RLock` 保护 `c.connection`。
    -   修复 `keepAlive` 上下文问题。

2.  **阶段二：修复 SSH Pool 连接泄漏 (高优先级)**
    -   修改 `GetConnection` 逻辑：当连接繁忙时，返回临时连接而不修改 map。
    -   修改 `ReleaseConnection` 逻辑：支持识别是否需要归还（或者由调用方根据 `isTransient` 标志决定是 `Release` 还是 `Close`）。
    -   由于 `InteractBasic` 是主要调用方，需要配合修改。

3.  **阶段三：验证**
    -   编写并发测试用例（模拟多个协程对同一 IP 的采集）。
    -   监控 TCP 连接数，确认无泄漏。
