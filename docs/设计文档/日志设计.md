# 日志设计（现状分析与改进建议）

## 1. 范围与目标

本文只基于当前仓库代码对日志实现做“现状分析 + 优缺点 + 改进建议”，覆盖：

- 系统运行日志：启动/停止、配置热更新、模拟服务启停、数据库初始化等
- 接口调用行为日志：HTTP 请求访问、请求标识（Request ID）、错误返回等
- 业务任务日志：采集（collector）、备份（backup）、下发（deploy）、格式化（format）相关的任务追踪与输出摘要
- 存储方式：控制台/文件、轮转/压缩、按任务文件等

不包含代码修改方案落地，只给出建议。

### 2.2 HTTP 访问日志（Gin 中间件 + 自定义中间件）

路由初始化位于 [router.go](file:///Users/wangfuyu/PythonCode/SSH-GO/api/router/router.go#L15-L196)：

- Gin 内置：
  - `gin.Logger()`：默认访问日志（输出到 Gin 的 writer，通常是 stdout）
  - `gin.Recovery()`：panic 恢复与错误输出（通常是 stderr）
- 自定义：
  - `RequestIDMiddleware()`：读取/生成 `X-Request-ID` 并写入响应头与 context（见 [router.go](file:///Users/wangfuyu/PythonCode/SSH-GO/api/router/router.go#L219-L230)）
  - `LoggingMiddleware()`：在请求结束后记录 method/path/status/duration 等（见 [router.go](file:///Users/wangfuyu/PythonCode/SSH-GO/api/router/router.go#L232-L275)）

因此，HTTP 请求会产生两路访问日志：

- Gin 默认访问日志（与本项目 logrus 体系不一致）
- 自定义 `LoggingMiddleware` 的应用日志（走 logrus / lumberjack）

### 2.3 任务级日志（按任务文件 + 全局结构化日志）

当前存在“按任务文件”的设计，主要用于 collector 与 backup：

- Collector：创建 `logs/collection/<task_id>_<YYYYMMDD_HHMMSS>.log` 并写入 JSONL（见 [collector.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/collector.go#L313-L502)）
- Backup：创建 `logs/backup/<task_id>_<YYYYMMDD_HHMMSS>.log` 并写入 JSONL（见 [backup.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/backup.go#L635-L876)）
- 交互执行链路（登陆成功/失败、逐命令 task_trace）：会额外写入全局日志（见 [interact_basic.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/interact_basic.go#L507-L556)）

Deploy 与 Format：

- Deploy：响应里返回的 `LogFilePath` 指向全局应用日志文件（`cfg.Log.FilePath`），并没有独立“按任务文件”（见 [deploy.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/deploy.go#L117-L122)）
- Format：主要使用全局日志记录告警/错误（例如写 MinIO 失败），无独立按任务文件（见 [format.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/format.go#L422-L468)）

### 2.4 数据库日志（GORM）

SQLite 初始化处为 GORM 配置了日志输出（见 [sqlite.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/database/sqlite.go#L21-L74)）：

- Writer：复用 `logger.GetLogger()`（logrus）
- GORM 日志级别：`Warn`
- 慢查询阈值：`1s`

这意味着 GORM 产生的日志会进入全局日志文件/控制台（取决于 log.output 配置），但日志内容本质仍是“拼接后的文本消息”，不是结构化字段。

但当前 `internal/config.LogConfig` 与 `pkg/logger` 都未定义/解析 `modules`，因此该配置不会生效（配置漂移/误导风险）。

## 4. 日志格式、等级与内容模板

### 4.1 全局应用日志格式（logrus）

#### JSON 模式

- 时间格式：`2006-01-02 15:04:05`
- JSONFormatter 默认字段通常为：
  - `time`
  - `level`
  - `msg`
  - 以及通过 `WithField(s)` 注入的额外字段

实现见 [logger.go](file:///Users/wangfuyu/PythonCode/SSH-GO/pkg/logger/logger.go#L37-L48)。

#### Text 模式

- 全时间戳：`FullTimestamp=true`
- 时间格式同上

实现见 [logger.go](file:///Users/wangfuyu/PythonCode/SSH-GO/pkg/logger/logger.go#L43-L48)。

#### 重要现象：Key-Value 形式“看起来结构化”，实际不是结构化

大量调用使用了类似：

```go
logger.Info("Server starting", "port", cfg.Server.Port, "mode", cfg.Server.Mode)
```

但 `pkg/logger` 的 `Info(args ...interface{})` 只是把所有参数交给 `logrus.Logger.Info(args...)`（见 [logger.go](file:///Users/wangfuyu/PythonCode/SSH-GO/pkg/logger/logger.go#L98-L102)），logrus 会将这些参数拼接成一段 message，而不会自动解析成字段。

结果：

- JSON 模式下：通常只有 `msg` 一个大字符串，`port/mode` 不会成为独立字段
- Text 模式下：同样是拼接后的字符串

真正的结构化字段只在 `WithField/WithFields` 时生效（例如采集任务命令队列的记录见 [collector.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/collector.go#L381-L388)）。

这会直接影响“可检索性/可聚合性/可观测性”（例如无法按 request_id、task_id、device 等做字段级过滤与统计）。

### 4.2 任务日志（按任务文件）的格式与模板

Collector/Backup 的按任务文件是 JSON Lines（一行一个 JSON），字段模板大致为：

- 通用字段：
  - `time`：字符串时间戳（`2006-01-02 15:04:05`）
  - `level`：`info/warn/error`（小写）
  - `log_type`：`collection` 或 `backup`
  - `task_id`
  - `msg`
- 逐命令追踪（task_trace）字段：
  - `device`
  - `command`
  - `status`：`成功/失败`
  - `exit_code`
  - `duration_ms`

Collector 写入处见：

- 基础 info/error/warn 行： [collector.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/collector.go#L825-L933)
- 逐命令 task_trace 行： [collector.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/collector.go#L884-L933)

Backup 写入处见：

- 登陆失败写入 `__login__`： [backup.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/backup.go#L752-L787)
- 逐命令 task_trace： [backup.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/backup.go#L829-L875)

### 4.3 接口调用日志模板（HTTP Request / HTTP Error）

自定义中间件在请求结束后记录：

- `request_id`、`method`、`path`、`status`、`duration`、`client_ip`、`user_agent`

实现见 [router.go](file:///Users/wangfuyu/PythonCode/SSH-GO/api/router/router.go#L232-L274)。

但由于 4.1 中提到的“KV 不会转字段”，这套模板目前落到文件里更像一条拼接 message，而不是可直接聚合的字段集。

### 4.4 调试输出模板（命令输出摘要）

在 debug 级别下，会记录命令输出的 head/tail 行摘要（见 [output_parser.go](file:///Users/wangfuyu/PythonCode/SSH-GO/pkg/logger/output_parser.go#L105-L118) 以及 SSH 执行处 [client.go](file:///Users/wangfuyu/PythonCode/SSH-GO/pkg/ssh/client.go#L351-L405)）。

该设计对排障有价值，但需要注意：

- 输出内容可能包含敏感信息（配置片段、账号信息等），在生产环境建议默认关闭或做脱敏/采样策略

## 5. 存储方式与生命周期（轮转/清理）

### 5.1 全局日志文件（可轮转）

由 lumberjack 管理，支持：

- 按大小轮转、保留份数、保留天数、压缩
- 输出可选 console/file/both

实现见 [logger.go](file:///Users/wangfuyu/PythonCode/SSH-GO/pkg/logger/logger.go#L50-L75)。

### 5.2 按任务日志文件（当前无轮转）

Collector/Backup 的任务日志写入 `logs/collection`、`logs/backup` 目录，但没有：

- 基于大小/时间的轮转
- 基于保留策略的清理
- 与任务生命周期/状态联动的归档

因此长期运行会累积较多任务日志文件，需要外部运维策略或后续在代码层补齐“清理/归档/上传对象存储”等能力。

### 5.3 Gin 默认日志通道（未与全局日志统一）

`gin.Logger()` 与 `gin.Recovery()` 走 Gin 的默认输出通道（stdout/stderr），不会进入 lumberjack 的文件轮转体系，导致：

- 同一请求可能在两个地方分别记录
- 线上排障需要同时看 stdout/stderr 与应用日志文件

## 6. 日志查询与展示（接口 + 前端）

### 6.1 日志查询接口

提供了 `GET /api/v1/logs/tail`，从 `cfg.Log.FilePath` 读取全局日志文件并做简单过滤（见 [logs.go](file:///Users/wangfuyu/PythonCode/SSH-GO/api/handler/logs.go#L1-L104)）。

特点/限制：

- 读取方式：把整个文件逐行扫描到内存，再过滤并取尾部
  - 文件较大时内存与延迟不可控（即使只想取末尾 N 行）
- 过滤方式：`q`（包含匹配）+ `level`（粗糙匹配，兼容 json/text）
- 只支持一个文件：无法直接查询 `logs/collection/*`、`logs/backup/*` 等任务日志

### 6.2 前端页面参数不一致风险

管理页 [logs.html](file:///Users/wangfuyu/PythonCode/SSH-GO/web/admin/logs.html#L1-L51) 中请求参数使用了 `lines/keyword`，而后端 `TailLogs` 使用 `limit/q`（见 [logs.go](file:///Users/wangfuyu/PythonCode/SSH-GO/api/handler/logs.go#L20-L33)），这会导致页面查询“看起来请求成功但筛选/行数不生效”的风险。

## 7. 优缺点分析

### 7.1 优点

- 依赖简单：logrus + lumberjack，上手成本低（见 [logger.go](file:///Users/wangfuyu/PythonCode/SSH-GO/pkg/logger/logger.go#L1-L77)）
- 支持文件轮转：适合长期运行的守护进程类服务
- 引入 Request ID：具备最基本的请求级关联能力（见 [router.go](file:///Users/wangfuyu/PythonCode/SSH-GO/api/router/router.go#L219-L230)）
- 任务日志“按文件隔离”：collector/backup 都能返回 `log_file_path` 便于定位单任务问题（见 [collector.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/collector.go#L363-L375)，[backup.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/backup.go#L652-L657)）
- SSH 执行链路有 task_trace：登陆与逐命令可追踪（见 [interact_basic.go](file:///Users/wangfuyu/PythonCode/SSH-GO/internal/service/interact_basic.go#L507-L556)）

### 7.2 主要问题/不足

- 结构化日志不一致：
  - `WithFields` 是结构化的，但大量 `Info("x","k","v")` 并不会产生字段
  - 造成 JSON 日志难以按字段聚合/搜索/告警
- 日志通道割裂：
  - Gin 默认访问日志与 Recovery 不进入 lumberjack 文件
  - 同一请求的访问记录可能重复且格式不同
- 按任务文件缺少生命周期管理：
  - 无轮转/清理策略，长期运行可能导致磁盘压力
- 查询接口性能与覆盖面不足：
  - 全量读文件再取尾部，文件越大越慢
  - 只能查询全局日志，无法查询任务日志
- 配置漂移：
  - `log.modules.*` 存在但不生效，容易造成“以为生效但其实没生效”
- 热更新重初始化的并发风险：
  - `logger.Init` 会替换包级 `log` 指针（见 [logger.go](file:///Users/wangfuyu/PythonCode/SSH-GO/pkg/logger/logger.go#L26-L78)），若在高并发写日志时热更新，理论上存在数据竞争风险（需要结合 `-race` 才能确认）

## 8. 改进建议（按收益优先级）

### 8.1 统一结构化日志 API（最高优先级）

目标：让“字段”真正成为字段，避免拼接 message。

建议方向（任选其一）：

- 在现有 logrus 基础上补齐 `Infow/Warnw/Errorw`（或 `InfoKV`）风格 API：`msg + fields`，内部强制 `WithFields(fields).Info(msg)`
- 或引入 Go 标准库 `log/slog`（Go 1.21+）做统一结构化日志，再把 logrus 逐步迁移/兼容

落地收益：

- HTTP/任务/数据库/系统事件都可以按 `request_id/task_id/device/log_type` 维度聚合与告警

### 8.2 统一 HTTP 访问日志与 panic 恢复输出

目标：所有请求日志都进入同一日志体系（同格式、同轮转策略）。

建议方向：

- 移除 `gin.Logger()`，改为只使用自定义 `LoggingMiddleware`（结构化版本）
- 或将 Gin 的 writer 指向 lumberjack + stdout 的 MultiWriter，并实现与全局一致的格式
- Recovery：将 panic 信息也写入结构化日志（包含 request_id/path/method）

### 8.3 建立日志 Schema（字段规范）并固化

建议定义统一字段：

- 关联字段：`request_id`、`task_id`、`device`、`log_type`、`module`
- 结果字段：`status`、`duration_ms`、`exit_code`、`error`
- 资源字段：`client_ip`、`user_agent`

并约定：

- `msg` 只放人类可读摘要
- 大字段（命令输出、配置内容）默认不写入，或只写摘要/采样

### 8.4 任务日志文件治理

建议补齐：

- 清理策略：按天/按文件数/按总大小（例如保留 7 天），根据配置文件动态调整
- 归档策略：压缩、打包、可选上传到对象存储
- 查询能力：通过 API 查询指定 task_id 对应的任务日志（授权后），避免直接暴露文件系统路径

### 8.5 日志查询接口性能优化

目标：支持大文件尾部读取与流式返回。

建议方向：

- Tail 实现改为从文件末尾向前 seek（或使用 ring buffer），避免全量读入内存
- 支持分页/游标（cursor），配合前端实时刷新
- 支持轮转文件查询（collector.log.1 / 压缩包等）

### 8.6 安全与合规

- 明确哪些日志属于“审计日志”（如管理接口变更、平台参数更新），与运行日志分流存储
- 对命令输出、配置片段、凭证信息做脱敏策略（尤其是 debug 级别输出摘要）
